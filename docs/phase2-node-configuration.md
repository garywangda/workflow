# 第二轮：节点配置与表单设计

基线：`e0004f0`（第一轮 workflow）。开发分支：`feat/phase2-node-configuration`。

本文档以当前已经落地的实现为准，用于记录第二轮最终设计、相对于早期方案的修订、15 个预设的右侧设置，以及本轮明确不实现的运行边界。

## 1. 本轮最终结论

- 继续使用第一轮已经设计好的 Flow Editor，不新建或替换编辑器。
- 完整保留原有 7 类 Node Toolbar、二级预设菜单、Node 样式、连接点、连线、拖动、缩放、删除确认和画布布局。
- 第二轮的 15 个预设是“节点配置模型”，不是一套新的 Node Toolbar。用户仍按原方式把节点放到画布上，再在右侧 Inspector 中配置与节点类型兼容的预设。
- 新建流程默认创建一个“手动发起”节点，并固定附带一张 `Start form`。用户必须设计至少一个输入字段并完成字段绑定后，流程才可通过发布检查。
- 右侧 Inspector 可以选择已保存表单的指定版本，也可以创建新表单或基于当前表单继续编辑并保存为新版本。
- 表单设计器采用开源 Form.io 前端库，通过独立、同源 iframe 嵌入，避免其 Bootstrap 样式和拖拽事件干扰 React Flow 主画布。
- “事件触发”“调用外部服务”“等待事件”本轮不开放配置与执行；等确定第一批真实连接对象后再实现。
- 本轮完成的是流程设计和浏览器本地保存，不包含真正的流程运行、任务派发、通知发送、定时调度、人员目录或外部系统调用。

| 项目 | 早期设想或疑问 | 本轮定稿 |
| --- | --- | --- |

| Node Toolbar | 可能把 15 个预设直接铺到 Toolbar | Toolbar 保持原有 7 类和原二级菜单；15 个预设进入右侧配置模型 |

| 手动发起 | “直接发起，需要时再加表单”或“固定启动表单”二选一 | 采用固定启动表单；启动资料成为后续节点的初始流程数据 |
| 表单能力 | 自研表单模块或采用开源方案 | 采用 Form.io 前端设计器；主应用保存表单 schema、版本和字段绑定 |

| 外部连接 | 可能本轮同时实现外部服务和事件 | 本轮暂缓事件触发、调用外部服务、等待事件 |
| 并行冲突 | 早期文档写为后续扩展 | 当前已能检查两条并行分支在 Merge 前写入同一个流程字段，并阻止发布 |
| 发布 | 可能直接代表流程可运行 | 只发布不可变的设计快照，不启动流程实例 |

## 3. 右侧 Inspector 的通用结构

选中一个普通节点时，右侧面板统一包含以下区域：

1. **流程级操作**：`Check workflow` 和 `Publish version`。检查结果可以点击并定位到对应节点。
2. **节点基本信息**：节点名称和说明。
3. **兼容预设选择**：第一轮遗留节点尚未包含 `presetId` 时，根据原节点类型显示兼容的第二轮预设；不会改变节点的 React Flow type。
4. **Step settings**：显示当前预设专属的业务设置。
5. **Start form / Form and fields**：需要资料的节点可选择已保存表单、创建新表单或编辑当前表单。
6. **Timing and reminders**：人工填表、人工任务和审批可设置自然小时截止时间与提前提醒。
7. **Outputs and paths**：说明当前节点产生的数据，并配置出口名称；条件与审批必须明确指定语义出口。

未选中节点时，Inspector 显示流程级设置、检查与发布入口，以及当前流程可供后续节点使用的数据字段。选中图形元素时仍显示第一轮的 Diagram Inspector，不套用业务节点配置。

所有修改继续通过 React Flow 的 `updateNodeData`、`setNodes` 和 `setEdges` 写回现有文档状态，再沿用第一轮 `DocumentContext` 自动保存；单个节点组件不直接访问存储。

## 4. 15 个预设及右侧设置

| # | 原节点类型 | 第二轮预设 | 右侧主要设置 | 用户逻辑与本轮可行性 |
| --- | --- | --- | --- | --- |
| 1 | Trigger | 手动发起 `Manual` | 可发起人范围、人员/角色 ID、流程实例标题规则、固定启动表单 | 已落地设计与校验。新流程默认拥有该节点和启动表单；尚不能真正提交并启动实例 |
| 2 | Trigger | 定时发起 `On a schedule` | 单次/每日/每周、首次执行时间、时区、结束时间、上次未结束时跳过或并行 | 配置和校验已落地；实际定时器和运行实例未实现 |
| 3 | Trigger | 事件触发 `On an event` | 未来需要连接对象、事件类型、过滤条件、去重键和载荷映射 | 本轮停用；没有真实系统时无法形成可验证闭环 |
| 4 | Form | 填写表单 `Fill out a form` | 办理人来源、单人办理/候选人认领、表单与字段、截止与提醒 | 已落地设计与校验；任务派发和提交记录未执行 |
| 5 | Human Task | 完成人工任务 `Complete a task` | 办理人、办理模式、工作说明、检查清单、是否要求附件、可选表单、截止与提醒 | 已落地设计与校验；附件仅为规则，尚无后端存储 |
| 6 | Approval | 审批 `Approval` | 审批人、全员通过/任一通过、驳回理由、是否允许退回、退回的填表节点、表单、截止与提醒 | 已落地设计与校验；通过和驳回各须唯一出口。退回后重新发起全员审批的规则已记录但未执行 |
| 7 | Action | 发送通知 `Send notification` | 接收人来源、站内通知标题与正文 | 已落地设计与校验；本轮只支持站内通知的设计数据，不真正发送，也不代表已读 |
| 8 | Action | 更新流程数据 `Update workflow data` | 目标流程字段、固定值、始终覆盖/仅为空时写入 | 已落地基础配置与类型校验；计算表达式和跨节点输出引用尚未实现 |
| 9 | Action | 调用外部服务 `Call external service` | 未来需要连接、动作、认证、输入映射、输出映射、超时、重试和幂等设置 | 本轮停用；待确定企业微信、钉钉、飞书、Webhook 或内部系统等第一批连接对象 |
| 10 | Logic | 条件分支 `Condition branch` | 流程字段、比较操作符、比较值、示例值测试、匹配与默认出口 | 已落地单条件配置、类型检查和两条必需出口；嵌套 AND/OR 与多条件优先级尚未实现 |
| 11 | Logic | 并行分支 `Parallel branches` | 配对 Merge、全部分支完成后汇合、失败时阻塞汇合 | 已落地结构检查；至少两条分支，所有分支必须到达配对 Merge，并检测并行写字段冲突 |
| 12 | Wait | 等待时间 `Wait for time` | 持续小时数/指定日期时间/日期字段、时区 | 已落地设计与校验；进入节点时解析日期、过去时间立即继续是运行规则，调度器未实现 |
| 13 | Wait | 等待事件 `Wait for event` | 未来需要连接对象、关联键、事件条件、超时出口和重复事件处理 | 本轮停用；与事件触发共用未来连接基础设施 |
| 14 | End | 正常结束 `Normal end` | 结果名称、结果摘要 | 已落地设计与校验；结束节点不能有后续出口，尚不生成真实运行结果 |
| 15 | End | 提前终止 `Early end` | 结果名称、结果摘要、业务终止原因、未完成任务处理 | 已落地设计与校验；当前规则为取消未完成任务和等待、保留已有结果、不回滚外部副作用，但尚未执行 |

其中 12 个预设可以在本轮配置，3 个与外部事件或服务有关的预设保持停用。这里的“已落地”均指设计界面、文档数据和发布前校验已经存在，不表示运行引擎已经存在。

## 5. 手动发起与固定启动表单

### 5.1 创建流程时的默认状态

当一个流程文件从未保存过画布文档时，编辑器自动创建一个位于画布初始区域的 `Manual` 节点，并在 `node.data.config.form` 中附带空的 `Start form`。固定的含义是“手动发起节点必须拥有启动表单”，不是预置一组不可修改的字段。

用户可以在右侧完成以下操作：

- 选择表单库中已经设计好的某个版本；
- 创建一张新表单并添加字段；
- 编辑当前表单，并将修改保存成同一表单的新版本；
- 在设计模式和预览模式之间切换；
- 为每个输入字段绑定稳定的数据字段并设置访问方式。

已有保存记录的流程按原文档打开，即使它是空画布也不会自动插入启动节点，避免静默改变用户已有内容。

### 5.2 表单字段与流程数据

表单控件支持文本、多行文本、数字、金额、日期、日期时间、选择、复选、布尔、人员标识、附件以及一层明细表。按钮不作为流程字段。

每个输入控件具有：

- 表单组件 `key`：对应控件在 schema 中的位置；同一表单内必须唯一。
- 稳定 `fieldId`：表示流程数据字段；修改显示名称不改变该 ID。
- 字段名称与类型：字段类型必须与表单控件兼容，直接改变已存在字段的类型会被拒绝。
- 节点访问方式：可编辑、只读或隐藏。
- 当前节点必填：只对可编辑字段有效；只读或隐藏字段不能同时设为必填。

新控件默认创建新的流程字段；用户也可以从当前流程中选择类型兼容的已有字段进行复用。后续节点通过 `fieldId` 引用启动表单产生的数据。

产品目标仍是允许字段映射到数据库中已有数据，但本轮仓库没有数据库或元数据接口。因此当前“已有字段”只来自同一流程各节点保存的表单快照，不等于任意数据库表字段。正式接入数据库时，应增加字段目录适配层，并保持现有 `fieldId` 作为稳定引用，避免把表名和列名散落到节点配置中。

### 5.3 表单版本策略

- 表单保存在 `workflow.forms.v1`，每次保存生成递增的新版本，不覆盖旧版本。
- 节点保存所选择表单版本的深拷贝快照。
- 编辑共享表单不会自动改变其他节点已经绑定的版本。
- 表单必须有名称；每个输入必须有唯一且类型兼容的数据绑定。
- 当前 Form.io 只使用前端库，没有连接 Form.io 服务器或托管平台。

## 6. 检查与发布规则

草稿允许暂时不完整；发布前执行检查。当前检查包括：

- 流程必须恰好有一个启动节点，并至少有一个结束节点；
- 非结束节点必须连接后续节点，结束节点不能有出口；
- 连线不能引用已删除节点，流程不能包含循环；
- 第一轮遗留节点必须选择与类型兼容的第二轮预设；
- 启动或填表所用表单至少有一个输入，所有输入必须完成类型兼容的字段绑定；
- 指定发起人、办理人、审批人、通知接收人等必填对象不能缺失；人员字段来源必须引用 `person` 类型字段；
- 人工任务必须有工作说明；通知必须有标题和正文；提前终止必须有原因；
- 截止时间必须大于零，提醒必须发生在截止之前；时区必须有效；
- 审批必须各有一条 `approved` 和 `rejected` 出口，退回目标只能是填表节点；
- 条件分支必须有 `match` 和 `default` 出口，操作符和值必须与字段类型兼容；
- 等待时间或日期字段必须有效；
- 并行节点至少有两条分支，所有分支必须抵达配对 Merge；两条分支在汇合前写同一字段会被视为冲突；
- 停用的外部服务或事件预设不能发布。

点击检查问题会选择对应节点。检查通过后，`Publish version` 将当前文档深拷贝成不可变设计快照，保存到 `workflow.versions.{workflowId}`，版本号递增，并把流程库状态更新为已发布。发布后的新编辑仍留在草稿，并把流程标记为存在未发布修改。

发布按钮发布的是设计版本，不会真正发起流程、创建任务、发送消息或运行定时器。发布检查是编辑器级基础校验，不能替代未来运行引擎的完整语义验证。

## 7. 数据与运行边界

本仓库仍是浏览器端原型，没有服务器、数据库、人员目录、文件存储、任务执行引擎或调度服务。

| 数据 | 当前存储位置 | 当前含义 |
| --- | --- | --- |
| 流程草稿 | `workflow.document.{workflowId}` | React Flow nodes、edges 和节点配置 |
| 表单版本库 | `workflow.forms.v1` | Form.io schema、字段绑定和历史版本 |
| 发布版本 | `workflow.versions.{workflowId}` | 通过检查后的不可变流程设计快照 |
| 流程列表 | 第一轮 `LIBRARY_KEY` | 名称、状态、更新时间等流程文件元数据 |

以下能力明确留给后续运行闭环：

- 启动表单提交与流程实例数据快照；
- 真实数据库字段目录和读写权限；
- 人员、角色、组织目录解析与无人匹配时的转派；
- 任务创建、认领、完成、审批意见和在途版本固定；
- 提醒调度、站内通知投递与已读状态；
- 附件上传、病毒扫描、权限和生命周期；
- 外部连接、认证、Webhook、幂等、重试和补偿；
- 复杂条件、多条规则、计算表达式及完整流程模拟器。

## 8. Canvas 核心边界

`WorkflowCanvas.tsx` 未修改。Node Toolbar、节点创建工厂入口、连线 handlers、四个 Handles、吸附参数、节点拖动、视口、缩放和删除确认逻辑保持第一轮版本。

第二轮只在 Inspector、配置模型、表单设计器和流程文件初始化层增加能力。若以后确实必须修改 Canvas 核心，应满足以下条件：改动范围极小、说明不可替代的原因、不改变现有行为，并先增加相应 regression test。

`phase2-canvas.test.tsx` 使用真实 React Flow 验证原有节点放置、既有连线保留，以及取消/确认删除行为。

## 9. 当前已知限制

- 定时发起、等待时间、通知、人工任务和审批目前只保存规则，不执行。
- 条件编辑器目前只支持一个字段的一次比较；复杂嵌套 AND/OR、多条优先条件仍需扩展。
- 数据更新目前只支持一个字段的固定值写入；计算和跨节点输出引用仍需扩展。
- 并行写冲突可以检测，但还没有“显式合并数据”的专用节点配置。
- 人员使用稳定 ID 占位，附件仅保存字段定义，均需后端服务。
- 表单库和流程数据保存在当前浏览器，清理浏览器数据会丢失。
- Form.io 可视化设计器的部分高级编辑能力可能按组件加载官方 CDN 资源，正式离线部署前需完成资源本地化。

## 10. 验证方式

自动验证：

```text
npm test
npm run typecheck
npm run lint
npm run build
npm run test:styles
git diff --check
```

浏览器主路径：创建流程 → 自动出现 Manual 节点 → 选中节点 → 编辑启动表单 → 拖入 Text Field → 修改标签 → 检查字段绑定 → Preview → Design → Save form → 重新打开并选择已保存版本。

原编辑器回归路径：从原 Node Toolbar 放置节点 → 拖动和连接 → 检查四个 Handle 与预览位置 → 右键删除并取消 → 再次删除并确认 → 验证原节点样式和画布行为没有变化。
